3. 플러그인/스킬화(Skillization) 필요성 및 오버엔지니어링 비판적 검토

본 연동 메커니즘을 Antigravity 커스텀 스킬(Skill)로 전환하는 것이 적합한지, 혹은 오버엔지니어링(Over-Engineering)인지를 3가지 핵심 축으로 비판 검토합니다.

1. 오버엔지니어링 인가? (Over-Engineering Check) ➔ 아니다 (Not Over-Engineered)
- 만약 무거운 별도 C++ 듀얼 프로세스, 컴파일된 바이너리, complex RPC 소켓 데몬 등을 새로 만든다면 명백한 오버엔지니어링입니다.
- 하지만 Antigravity 스킬(Skill)은 단순한 Markdown (`SKILL.md`) 가이드 문서 기반으로 동작합니다. **추가 런타임 부하나 종속성이 0%**이므로 스킬화하는 것은 가장 가볍고 효율적인 설계입니다.
2. 스킬화가 반드시 필요한가? (Necessity Check) ➔ 필수적이다 (Mandatory)
- **단위 트랩**: Fusion 360 API 내부 단위는 `cm`이나 사용자 치수는 `mm`입니다. 스킬이 없으면 다음 대화 세션의 AI가 이 단위 변환 법칙을 잊어버리고 10배 스케일 오류를 일으킵니다.
- **읽기 전속 속성 충돌**: `doc.name`, `root_comp.name` 설정 시 Fusion 360이 즉시 크래시나는 원리를 스킬 규격에 캡슐화해야 다음 대화에서도 안전이 보장됩니다.
- **CustomEvent 메인 스레드 마샬링**: REST 통신 수신 시 UI 스레드 안전성을 유지하는 파이썬 이벤트 템플릿을 스킬화해야 미래 프로젝트에 즉시 재사용이 가능합니다.
